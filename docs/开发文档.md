## 第 1 章 可行性评估

### 1.1 结论

**技术上完全可行，没有阻塞性障碍。**

本项目需要的每一项能力都有 uni-app 官方 API 支撑：不需要写原生代码、不需要服务器、不需要应用商店账号。唯一一个尚存疑问的点是"本地通知是否依赖推送模块"，第 7.4 节给出了 10 分钟内就能判定完的实测步骤。

### 1.2 能力清单（已核对官方文档源码）

| 需要的能力 | 官方 API | 版本门槛 | 备注 |
| --- | --- | --- | --- |
| 本地存储 | `uni.setStorageSync` / `uni.getStorageSync` | 全版本 | App 端底层是原生存储，**没有 H5 的 5MB 限制** |
| 弹通知栏 | `uni.createPushMessage({ title, content, delay, when, channelId })` | HBuilderX **3.5.2+** | 官方原文：`delay` 是"提示消息延迟显示的时间……单位为 s" |
| 通知渠道 | `uni.getChannelManager().setPushChannel()` | HBuilderX **4.02+**，Android 8.0+ | 可控制声音、震动、重要级别 |
| 云打包 | HBuilderX「发行 → 原生 App-云打包」 | — | 免费，公共测试证书足够自用 |

> 核对来源：`dcloudio/unidocs-zh` 仓库的 `docs/api/plugins/push.md`（uni-app 官方文档源码）。

**`uni.createPushMessage` 完整参数表**（第 7 章实现时直接照这个写）：

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `title` | string | 否 | 通知标题，默认取 App 名称 |
| `content` | string | **是** | 通知正文 |
| `payload` | string / Object | 否 | 自定义数据，点通知进入 App 时取回 |
| `sound` | string | 否 | `system`（默认）/ `none`。**App 在前台时提示音不生效** |
| `cover` | boolean | 否 | 是否覆盖上一条通知 |
| **`delay`** | number | 否 | **延迟多少秒后显示**，默认 0（立即）。这是"到点提醒"的关键 |
| `when` | Date | 否 | 通知上显示的时间 |
| `channelId` | string | 否 | 通知渠道 id，需 HBuilderX 4.02+ |

### 1.3 三个必须知道的风险点

#### 风险 1：App 被系统清理后，提醒可能失效 ⚠️ 中风险

- **事实**：官方文档对 `delay` 只写了"延迟显示"，**没有承诺 App 进程被杀后仍然生效**。按实现原理推断，它由 App 进程内的定时器驱动。
- **影响**：任务到点时，如果 App 已被系统或用户清理，通知不会弹出。
- **对策（本项目采用）**：
  1. **重排机制**：每次 App 启动、切回前台时，把所有"未完成且设有提醒时间"的任务重新调度一遍，并把已错过的提醒立即补发。
  2. **用户侧保活**：在 HyperOS 上开启自启动、把省电策略设为"无限制"（菜单路径见 1.4 节）。
  3. **升级路径**：若日后确实无法忍受漏提醒，改用插件市场的原生 AlarmManager 定时通知插件，方案对比见第 7 章。
- **验收口径**：本项目**不承诺"杀掉 App 也准时响"**。承诺的是"App 在后台或前台时准时响；重新打开 App 时补发漏掉的提醒"。

#### 风险 2：本地通知是否依赖 UniPush 模块 ⚠️ 待实测（全项目唯一未知项）

- **事实**：官方文档明确「UniPush 模块需要开通后才能提交云端打包，否则会提示错误」，但**没有说明 `createPushMessage` 是否依赖该模块**。
- **若确实依赖**：需要在 DCloud 完成实名认证并免费开通 UniPush，额外花约 10 分钟，**不产生任何费用**。
- **判定方法**：见 7.4 节的最小 demo 实测步骤。

#### 风险 3：Android 13+ 的通知权限 ⚠️ 低风险

- **事实**：Android 13（API 33）起发通知需要 `POST_NOTIFICATIONS` 运行时权限。uni-app 框架**默认会自动申请**（官方提供 `dcloud_push_auto_request_permission` 开关可关闭该行为）。
- **对策**：在设置页放一个"通知权限未开启 → 点此去开启"的引导项；打包指引里写明手动开启的菜单路径。
- **注意**：用户拒绝授权后**不要每次启动都重复弹窗申请**，官方文档明确提示过这一点。

## 第 2 章 项目概述

### 2.1 一句话定位

**一个只问你「还有什么要做」的本地待办清单。**

### 2.2 它解决的真正问题

市面上的待办 App 大多在解决"如何管理复杂项目"，于是塞进了项目、标签、团队、看板、甘特图、会员体系。结果是：**记一件小事要经过 5 次点击、3 个决策**，人还没开始做事就已经累了。

「还有什么」只解决一个问题：**让我在 3 秒内把脑子里的一件事记下来，做完打勾。**

### 2.3 目标用户与使用场景

**目标用户**：只有一个人——本人。单机使用，不涉及任何他人的数据。

**典型场景**：

| 场景 | 用户动作 | App 的响应 |
| --- | --- | --- |
| 突然想起一件事 | 掏出手机 → 打开 App → 输入一句话 → 回车 | 立即出现在列表顶部，不需要选分类、填日期、挑优先级 |
| 想起"这事下午三点前得办" | 点进这条任务，设一个提醒时间 | 到点弹通知栏提醒 |
| 办完一件事 | 点一下任务前面的圆圈 | 圆圈打勾、文字变灰、轻提示「还剩 N 件」 |
| 想确认"今天还有什么没做" | 打开 App 直接看列表（未完成在上） | 一眼扫完，不用翻页、不用筛选 |
| 想找一件旧事 | 顶部搜索框输入关键词 | 实时过滤出结果 |

### 2.4 明确「不做什么」

这一节和功能清单同等重要——**划掉的需求才是这个 App 能被做出来的原因**。

| 不做的事 | 原因 |
| --- | --- |
| 云同步 / 多设备 | 需要后端服务与账号体系，复杂度上升一个量级 |
| 账号 / 登录 | 单机自用，没有登录的必要 |
| 多人协作 / 分享 | 目标用户只有一个人 |
| 子任务 / 检查项 | 会让数据结构复杂化，且实际使用率极低 |
| 重复任务（每天 / 每周） | 需要一套循环规则引擎，收益不抵成本；留到第 9 章「后续版本」再议 |
| 日历视图 | 列表 + 截止时间已够用 |
| 桌面小组件 | 需要原生插件，与"云打包零插件"基线冲突 |
| 统计图表（完成率 / 周报） | 个人待办不需要 KPI 汇报 |
| 语音 / 视频附件 | 纯文本 + 图片已够用；语音要额外处理录音权限与音频编码 |
| 图片附件 | **已从「不做」改成「支持」**（可选功能，见 F7.5）：图片文件放应用私有目录、任务里只存路径；代价是**导出备份不含图片** |
| 多主题换肤 | 只做「浅色 / 深色 / 跟随系统」三态 |
| iOS / 小程序 / H5 | 只打包 Android，省掉全部多端适配成本 |
| 上架应用商店 | 自己用，公共测试证书签名直接安装 |
| 任何形式的联网 | 一旦联网就要处理权限申请、隐私政策与合规 |

> 日后若想加其中任何一项，先回来改这一章，再动手写代码。

**F1.1 新建任务 · P0**

- 入口：首页顶部输入框（占位符即文案 C2）
- 行为：输入文字后回车，任务立即创建并出现在列表顶部，输入框清空并保持聚焦，方便连续录入
- 验收标准：
  1. 输入「买牛奶」回车 → 列表顶部立即出现「买牛奶」，状态为未完成
  2. 输入空白或纯空格后回车 → **不创建任务**，不报错，不出现空行
  3. 连续创建 3 条 → 按创建时间倒序（最新在上）
  4. 关闭 App 再打开 → 3 条都还在

**F1.2 编辑任务 · P0**

- 入口：点击任务行的文字区域 → 进入编辑页
- 可修改：标题、备注、所属分类、提醒时间、截止时间
- 返回时**自动保存**（不设"保存"按钮，减少一次点击），仅在标题被清空时提示「内容不能为空」并拒绝保存
- 验收标准：
  1. 改标题后返回 → 列表立即显示新标题
  2. 清空标题后返回 → 提示「内容不能为空」，停留在编辑页
  3. 修改后重开 App → 修改已生效

**F1.3 删除任务 · P0**

- 入口：任务行**左滑** → 露出「删除」按钮
- 验收标准：
  1. 左滑后点删除 → 任务从列表消失
  2. 删除后底部弹出「已删除 · 撤销」，停留 5 秒
  3. 重开 App → 被删除的任务不再出现

**F1.4 撤销删除 · P1**

- 5 秒内点「撤销」→ 任务回到原位置（含原有分类、提醒时间）
- 超时后提示自动消失，删除成为最终状态

**F1.5 勾选完成 / 取消完成 · P0**

- 入口：点击任务行左侧的圆圈
- 验收标准：
  1. 点击未完成任务的圆圈 → 圆圈填色打勾、标题变灰加删除线，随后移入已完成分组
  2. 底部轻提示「还剩 N 件」（文案 C4），N 为当前未完成数
  3. 再点一次已完成任务的圆圈 → 回到未完成分组，提示数字回增
  4. 全部完成时提示改为「没有别的了」
  5. 重开 App → 完成状态保持
  6. 已完成的任务**不再触发提醒**

**F2.1 首页任务列表 · P0**

**F7.1 本地持久化 · P0**

- 验收：开启飞行模式 → 全部功能正常；断网状态下增删改查无任何报错

**F7.2 首次启动的权限引导 · P0**

- **不得**每次启动重复弹窗申请
- 验收：首次安装启动 → 出现系统通知权限弹窗；拒绝后设置页出现提示行

**F7.3 关于页 · P1**

- 内容：App 名、版本号、一句话定位、以及「所有数据仅保存在本机」的说明
- 验收：设置页底部可见「关于」，点进去能看到上述四项

**F7.4 数据导出与导入 · P1**

- 位置：设置页「数据」分区，两个入口——「导出数据」（值显示：复制到剪贴板）、「导入数据」（值显示：从剪贴板恢复）
- **导出流程**：点击 → 生成带缩进的 JSON → `uni.setClipboardData` 写入剪贴板 → 弹窗告知「共 N 条任务（已完成 M 条）、K 个分类」，并提示自行粘贴保存
- **导入流程**：点击 → `uni.getClipboardData` 读取 → 六重校验 → 弹窗说明「备份里有 N 条任务、K 个分类，会覆盖当前全部数据」→ 用户确认后覆盖
- **六重校验**（任一不通过都拒绝，并给出中文原因）：
  1. 文本为空
  2. 不是合法 JSON
  3. JSON 是数组而不是对象
  4. `app` 字段不是 `whatelse`（不是本 App 导出的备份）
  5. `schemaVersion` 高于当前版本（来自更新版本的 App）
  6. 缺 `tasks` 或 `categories` 数组
- **验收标准**：
  1. 建 3 条任务 → 点导出 → 弹窗提示已复制且条数正确 → 粘贴到备忘录能看到完整 JSON
  2. 复制那段 JSON → 点导入 → 确认后任务与分类全部恢复
  3. 复制一段无关文字再点导入 → 提示「这不是「还有什么」导出的备份」，数据不变
  4. 导入确认框点「取消」→ 数据不变

## 第 4 章 界面设计

### 4.1 设计原则

整体风格：**可爱风**（不是极简冷淡风）——圆润的形状、糖果色、带一点小情绪的反馈。

| 原则 | 具体做法 |
| --- | --- |
| **少一层就快一秒** | 新建任务不跳页面：首页顶部输入框直接敲，回车即成 |
| **一屏看完** | 不设分页、不设"加载更多"；所有操作在首页完成 |
| **点击区域够大** | 任务行最小高度 108rpx，勾选圆圈的热区放大到 88rpx |
| **形状要圆** | 全局圆角 28rpx 起步，胶囊用 999rpx；投影用主色半透明的"柔光"而不是灰黑 |
| **颜色要甜** | 主色是一对糖果渐变（草莓粉 → 香芋紫），完成色用薄荷青，背景带一点暖调 |
| **反馈要有小情绪** | 勾选时震动一下并轻微弹跳；空状态用会浮动的 emoji；选中的筛选胶囊会向上浮 2rpx |
| **颜色只做一件事** | 颜色只用来区分分类，不用来表示优先级（本项目没有优先级） |

### 4.7 暗黑模式实现方式

1. 在 `App.vue` 中引入一份 CSS 变量文件，定义 `:root` 下的浅色值。
2. 通过根节点（`page` 或自定义 `view`）的 class 切换：`.theme-light` / `.theme-dark`。
3. 主题状态存在 `whatelse_settings.theme`，取值 `system | light | dark`。
4. 选 `system` 时用 `uni.onThemeChange` 监听系统切换；App 端也可用 `@media (prefers-color-scheme: dark)` 兜底。
5. **不修改任何组件的内联颜色**，一律引用 CSS 变量，保证换肤只有一处改动。
6. `pages.json` 中同时配置 `"darkmode": true`，让原生导航栏跟随系统深浅色。

## 第 5 章 数据设计

### 5.1 存储总览

全部数据存在本机，**没有任何网络请求**。使用 uni-app 的键值存储 API，键名统一加 `whatelse_` 前缀。

| 存储键 | 类型 | 内容 | 写入时机 |
| --- | --- | --- | --- |
| `whatelse_tasks` | Array | 全部任务对象 | 每次任务增 / 删 / 改后立即写 |
| `whatelse_categories` | Array | 全部分类对象 | 分类增删改后立即写 |
| `whatelse_settings` | Object | 设置项 | 设置变更后立即写 |
| `whatelse_schema_version` | Number | 数据结构版本号，当前为 `1` | 仅在迁移时写 |
| `whatelse_backup_v0` | Array | 迁移前的旧数据备份（首次迁移时生成） | 仅迁移时写 |

### 5.2 Task 任务对象

| 字段 | 类型 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | string | 是 | — | 唯一 id，生成规则：`Date.now().toString(36)` + `-` + 4 位随机 36 进制，如 `lz3k9a-x8f2` |
| `title` | string | 是 | — | 任务内容，**1~200 字**，前后空格自动去除 |
| `note` | string | 否 | `''` | 备注，0~500 字 |
| `images` | string[] | 是 | `[]` | **图片路径数组**（可选功能，最多 9 张）。存的是应用私有目录路径，**不是 base64**——base64 会让本地存储迅速膨胀 |
| `done` | boolean | 是 | `false` | 是否已完成 |
| `categoryId` | string | 是 | `'default'` | 所属分类的 `id`；分类不存在时回落到 `'default'` |
| `remindAt` | number \| null | 是 | `null` | **提醒时间戳（毫秒）**，null = 不提醒 |
| `dueAt` | number \| null | 是 | `null` | **截止时间戳（毫秒，精确到分）**，null = 不设截止 |
| `createdAt` | number | 是 | 当前时间 | 创建时间戳（毫秒） |
| `updatedAt` | number | 是 | 当前时间 | 最后修改时间戳（毫秒） |
| `completedAt` | number \| null | 是 | `null` | 完成时间戳；取消完成时重置为 null |
| `sort` | number | 是 | = `createdAt` | 排序权重，供 F2.4 使用 |

**示例**：

```json
{
  "id": "lz3k9a-x8f2",
  "title": "买牛奶",
  "note": "顺路去超市",
  "done": false,
  "categoryId": "life",
  "remindAt": 1758783600000,
  "dueAt": null,
  "createdAt": 1758780000000,
  "updatedAt": 1758780000000,
  "completedAt": null,
  "sort": 1758780000000
}
```

> **`remindAt` 与 `dueAt` 是两个独立字段**：前者决定什么时候弹通知（F4），后者只是"这件事的期限"，仅作展示与排序用。不要合并成一个字段。

### 5.3 Category 分类对象

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 唯一 id；内置分类用固定 id（见下表） |
| `name` | string | 分类名，**1~8 字**，不可重复 |
| `color` | string | 十六进制色值，如 `#34C759` |
| `builtin` | boolean | 是否内置分类 |
| `sort` | number | 显示顺序，越小越靠前 |

**内置分类的初始值**（首次启动时写入）：

| `id` | `name` | `color` | 可删除 |
| --- | --- | --- | --- |
| `default` | 默认 | `#8A8F99` | **否**（兜底分类，任何时候都必须存在） |
| `work` | 工作 | `#3A7AFE` | 是 |
| `life` | 生活 | `#34C759` | 是 |
| `study` | 学习 | `#FF9500` | 是 |

**删除分类时的数据一致性规则**（F3.1）：
1. 先把所有 `categoryId` 等于该分类的任务改为 `'default'`
2. 再从未完成列表移除该分类
3. **两步写盘之间不能抛异常**——若第二步失败，任务已归入「默认」，不会出现"孤儿任务"

### 5.4 Settings 设置对象

| 字段 | 类型 | 默认值 | 对应需求 |
| --- | --- | --- | --- |
| `theme` | string | `'system'` | F6.1，取值 `system` / `light` / `dark` |
| `sortBy` | string | `'created'` | F2.4，取值 `created` / `remind` |
| `completedCollapsed` | boolean | `true` | F2.2，已完成分组折叠状态 |
| `filterCategoryId` | string | `'all'` | F3.3，当前分类筛选（`all` = 全部） |
| `notifyGuideDismissed` | boolean | `false` | F7.2，权限提示条是否被手动关掉 |
| `lastReorderAt` | number | `0` | F4.3，上次重排提醒的时间戳 |

### 5.5 数据版本与迁移策略

- 版本号存在 `whatelse_schema_version`，**当前为 `1`**。
- `common/storage.js` 中维护迁移表：

```
const MIGRATIONS = {
  // 版本号: (oldData) => newData
  // 2: (d) => { d.tasks.forEach(t => t.priority = 0); return d }
}
```

- 启动流程：读 `whatelse_schema_version` → 若小于当前版本，**先把全部数据备份到 `whatelse_backup_v<旧版本>`**，再按版本号顺序逐个执行迁移函数，最后写回新版本号。
- 迁移函数必须**只增字段、不改字段名、不删字段**，保证任何一次升级都不会让用户丢数据。

### 5.6 容量与性能边界

| 项目 | 估算 |
| --- | --- |
| 单条任务序列化后 | 约 250 字节 |
| 1000 条任务 | 约 250 KB |
| App 端单键存储上限 | 远大于此（App 端底层为原生存储，无 H5 的 5MB 限制） |
| 列表渲染 | 预计日常 < 200 条，暂不启用虚拟列表；若超过 500 条再考虑 |

### 5.7 读写时机

| 时机 | 动作 |
| --- | --- |
| App 启动 | 一次性把 tasks / categories / settings 读入内存（同步读） |
| 任务增删改 | **改内存 + 立即同步写盘**，保证任何时刻断电都不丢数据 |
| 设置变更 | 同上 |
| 切到后台 | 无需额外操作（已在每次修改时写盘） |

> 刻意不做"定时批量写盘"：数据量只有几百 KB，同步写的耗时在毫秒级，用简单换可靠。

### 6.2 三层架构与依赖方向

| 层 | 位置 | 职责 | **明令禁止** |
| --- | --- | --- | --- |
| **页面层** | `pages/`、`components/` | 渲染、用户交互、调用 service 后更新本地状态 | ❌ 不直接读写 `uni.setStorageSync`；❌ 不写业务规则（如"删除分类时迁移任务"） |
| **服务层** | `common/*Service.js` | 业务规则、数据校验、多步操作的编排 | ❌ 不碰 UI；❌ 不调 `uni.navigateTo` / `uni.showToast`；❌ 不直接调 `uni.setStorageSync` |
| **存储层** | `common/storage.js` | 键值读写、首次初始化、版本迁移 | ❌ 不含任何业务判断 |

**依赖方向严格单向**：`页面 → 服务 → 存储`。反向调用一律不允许。

**数据流示例**（勾选完成一条任务）：

```

    → storage.saveTasks(tasks)        // 存储层：uni.setStorageSync
    → notify.cancelTask(id)           // 服务层：已完成的任务取消提醒
  ← 返回 { task, remaining }
  → 页面用它更新列表 + 弹 Toast「还剩 N 件」
```

| 错误处理 | service 层遇到非法输入返回 `null` 或空数组，**不抛异常**；页面层负责把 `null` 转成用户可见的提示 |

## 第 7 章 提醒通知方案

本章是整个项目**技术风险最集中**的地方，实现时逐字照做，不要临场简化。

### 7.1 整体流程

```
任务设置了 remindAt（毫秒时间戳）
      ↓
notify.scheduleTask(task)
      ↓ 计算 delay = (remindAt - Date.now()) / 1000
      ↓
uni.createPushMessage({ title, content, payload, delay, when, channelId })
      ↓
到点 → 系统通知栏弹出（即使 App 在后台）
```

**没有服务器、没有推送证书、没有长连接**——纯粹靠系统本地的延迟通知机制。

### 7.2 核心实现（可直接照抄）

`common/notify.js`：

```js
const CHANNEL_ID = 'whatelse_default'
const WEEK_MS = 7 * 24 * 60 * 60 * 1000
const DAY_MS  = 24 * 60 * 60 * 1000

// 为单个任务安排提醒
export function scheduleTask(task) {
  if (!task || !task.remindAt || task.done) return

  const delta = task.remindAt - Date.now()
  if (delta < 0) return            // 已错过，交给 rescheduleMissed()
  if (delta > WEEK_MS) return      // 超 7 天，等进入窗口后由 scheduleAll() 补排

  uni.createPushMessage({
    title: '还有什么',
    content: task.title,
    payload: { taskId: task.id },
    sound: 'system',
    cover: false,
    delay: Math.round(delta / 1000),      // 单位：秒
    when: new Date(task.remindAt),
    channelId: CHANNEL_ID
  })
}

// 取消某个任务的提醒：cover 机制无法撤回已排期的消息，
// 因此取消 = 标记任务已完成（scheduleTask 会跳过），并在重排时不再排它
export function cancelTask(taskId) {
  // 见 7.3 的说明：原生 delay 通知无法真正撤回，靠"重排 + 已完成跳过"来等效实现
}

// 重排全部
export function scheduleAll() {
  queryTasks({ status: 'active' }).forEach(scheduleTask)
}

// 补发已错过的提醒
export function rescheduleMissed() {
  const now = Date.now()
  queryTasks({ status: 'active' })
    .filter(t => t.remindAt && t.remindAt <= now && now - t.remindAt < DAY_MS)
    .forEach(t => {
      uni.createPushMessage({
        title: '还有什么',
        content: t.title,
        payload: { taskId: t.id },
        sound: 'system',
        channelId: CHANNEL_ID
      })
    })
}
```

**参数用法对照**（每个参数为什么这么填）：

| 参数 | 值 | 理由 |
| --- | --- | --- |
| `title` | `'还有什么'` | 固定用 App 名，通知栏里一眼认出 |
| `content` | `task.title` | 任务内容就是通知正文 |
| `payload` | `{ taskId: task.id }` | 点通知时用它定位到具体任务（7.8） |
| `delay` | `Math.round(delta / 1000)` | **必须取整**；单位是秒不是毫秒 |
| `when` | `new Date(task.remindAt)` | 让通知上显示的时间是提醒时间而非当前时间 |
| `channelId` | `'whatelse_default'` | 与 7.7 创建的渠道一致，否则可能不响 |
| `cover` | `false` | 多条提醒各自显示，不互相覆盖 |
| `sound` | `'system'` | 用系统提示音；注意 **App 在前台时提示音不生效**（官方明确说明） |

### 7.3 调度时机与"7 天窗口"规则

| 触发时机 | 调用的函数 |
| --- | --- |
| App 启动（`App.vue` 的 `onLaunch`） | `initStorage()` → `rescheduleMissed()` → `scheduleAll()` |
| 从后台切回前台（`onShow`） | `rescheduleMissed()` → `scheduleAll()` |
| 新建 / 编辑任务（含改提醒时间） | `scheduleTask(task)` |
| 勾选完成 | 不再排（`scheduleTask` 里 `task.done` 直接 return） |
| 取消完成 | `scheduleTask(task)` |
| 删除任务 | 不排即可（重排时它已不在列表里） |

> **⚠️ 一个必须防住的坑：重复排期**
> `uni.createPushMessage` 排下的是「从此刻起延迟 N 秒」的通知，而上表的 `scheduleAll()` 会在每次启动和切回前台都执行。
> 如果不记账，同一个任务会被反复排期，**到点时会同一件事弹出好几条通知**。
> 因此 `notify.js` 里维护了一本**持久化的「已排期账本」**（存在 `settings.scheduledMap`，结构为 `{ taskId: remindAt }`）：
> 排期前先查账本，同一提醒时间只排一次；`remindAt` 变了才重新排；`scheduleAll()` 顺手清掉已完成/已删除任务的记录，避免账本无限增长。

**为什么限制 7 天窗口**：

`delay` 虽然可以填很大的值，但排期越远，中途 App 被清理、数据被修改、系统时间被调整的影响就越大。限制在 7 天内、并依靠"每次启动/回前台都 `scheduleAll()` 重排一次"的机制，可以把误差收敛到最近一次使用 App 之后。

> **⚠️ 一个必须知道的限制**：`uni.createPushMessage` 的原生实现**无法撤回已经排期的延迟通知**。所以"取消提醒"不是真的撤回，而是靠两条规则等效实现：
> 1. 已完成的任务在重排时会被跳过；
> 2. 用户改时间时，新通知会按时弹出，而旧通知因为 `cover: false` 可能仍会出现一次。
>
> **这是本方案公认的瑕疵**，验收时不要把它当 bug。若无法接受，走 7.6 的方案 B。

### 7.4 UniPush 模块是否必需：10 分钟实测步骤

**目的**：判定"本地通知"是否需要先开通 DCloud 的 UniPush 服务。

| 步骤 | 操作 |
| --- | --- |
| 1 | HBuilderX 新建一个**空白的 uni-app 项目**（Vue 3），页面用默认模板即可 |
| 2 | 在首页 `onLoad` 里加一行：`uni.createPushMessage({ title: '测试', content: '本地通知可用' })` |
| 3 | `manifest.json` → App 模块配置 → **不勾选**「Push(消息推送)」 |
| 4 | 发行 → 原生 App-云打包 → 打 Android 包（用公共测试证书） |
| 5 | 装到手机上打开，看是否弹出通知 |

**结果判定**：

| 现象 | 结论 | 下一步 |
| --- | --- | --- |
| 打包成功 + 打开 App 弹出通知 | ✅ **不依赖** | 按第 7 章原方案实现，`manifest.json` 里也不要勾 Push 模块 |
| 打包失败，提示需开通 UniPush | ❌ **依赖** | 去 [dev.dcloud.net.cn](https://dev.dcloud.net.cn/) 完成实名认证 → 开通 UniPush（免费）→ 勾选 Push 模块 → 重新打包 |
| 打包成功但打开 App 无通知 | ⚠️ 不确定 | 勾选 Push 模块后再打一次；若这次有了，说明依赖 |

> 这一步**必须在正式建项目之前做完**，因为它决定 `manifest.json` 的模块勾选，后补会导致反复重新打包。

### 7.5 HyperOS 用户侧设置（提醒准时率的关键）

详见 1.4 节的六项设置表。这里强调**必做的前三项**（缺任何一项都可能收不到提醒）：

1. **通知权限**：首次启动的弹窗选「允许」
2. **自启动**：设置 → 应用设置 → 应用管理 → 「还有什么」→ 自启动 → 打开
3. **省电策略**：同一页面 → 省电策略 → 选「**无限制**」

另外三项（后台弹出界面、锁定后台、安装未知应用）按 1.4 节操作。

### 7.6 已知限制与升级路径

| 方案 | 能力边界 | 代价 |
| --- | --- | --- |
| **A. 本方案**（纯 JS + `createPushMessage`） | App 在前台 / 后台时准时弹；App 被清理后需重新打开才补发 | 零插件、零成本、云打包最简单 —— **本项目采用** |
| **B. 原生通知插件** | App 被系统清理后也能准时弹（AlarmManager 级） | 需在云打包时勾选原生插件；插件质量参差、部分收费；每次打包都要重新制作自定义调试基座 |
| **C. 换 Flutter / 原生重写** | 完全可控 | 等于推倒重做，与当前投入产出不匹配 |

**从 A 升级到 B 的触发条件**（写死，避免凭感觉决策）：

> 在连续 30 天内，出现 **≥ 3 次**"因为 App 被系统清理而漏掉重要提醒"的情况。

达不到这个条件，就继续用方案 A。

### 7.7 通知渠道：一次性设定（一个容易踩的坑）

```js
// 放在 App.vue 的 onLaunch 里，首次启动执行一次
const manager = uni.getChannelManager()
manager.setPushChannel({
  channelId: 'whatelse_default',
  channelDesc: '任务提醒',
  importance: 4,          // IMPORTANCE_HIGH：会横幅弹出并响铃
  enableVibration: true,
  enableLights: false
})
```

**⚠️ Android 通知渠道的配置一旦创建就永久固化**，之后即使删除同 id 的渠道再重建也不会生效，除非卸载 App 重装。所以：

| 决策点 | 建议 | 理由 |
| --- | --- | --- |
| `importance` | **填 4**（HIGH） | 填低了通知只在通知栏里安静躺着，不横幅、不响铃，等于白提醒 |
| 以后要改铃声 / 震动怎么办 | **换一个新的 channelId**（如 `whatelse_default_v2`） | 同 id 改不动；换 id 等于新建渠道，可以带新配置 |
| 渠道的创建时机 | 第一次启动就建 | 晚了可能来不及，且要先于任何通知 |

### 7.8 点击通知进入 App 并定位到任务

```js
// App.vue 的 onLaunch
uni.onPushMessage((res) => {
  if (res.type === 'click') {
    const taskId = res.data && res.data.payload && res.data.payload.taskId
    if (taskId) {
      uni.navigateTo({ url: '/pages/task/edit?id=' + taskId })
    }
  }
})
```

> `payload` 在不同版本下的结构可能略有差异（可能是对象，也可能是 JSON 字符串）。实现时先 `console.log(res)` 看一眼真实结构，再取值。

### 7.9 怎么调试提醒

| 手段 | 说明 |
| --- | --- |
| **云打包后真机测试** | 最可靠。`createPushMessage` 属于原生能力，**标准基座真机运行可能不支持**，此时需要「制作自定义调试基座」 |
| 缩短等待时间 | 调试时把提醒时间设成 1~2 分钟后，不要设一小时后 |

| 验证补发逻辑 | 设一个 2 分钟后的提醒 → 下拉杀掉 App → 等 2 分钟 → 重开 App，应立即弹出补发通知 |

### 9.2 已确认事项（实施阶段开始时已定稿）

以下三项已由本人确认，代码严格按此执行。

**Q1：数据备份导出 —— 结论：v1 就做**

- 原计划排在 v1.1，现**提前到 v1**。
- 实现方式：不写文件、不联网，走系统剪贴板。
  - **导出**：`common/exportService.js` 的 `exportToText()` 生成带缩进的 JSON → `uni.setClipboardData` 复制到剪贴板，由使用者自行粘贴到微信收藏 / 备忘录 / 电脑保存。
  - **导入**：`uni.getClipboardData` 读回 → `parseImportText()` 六重校验 → 二次确认后 `applyImport()` 覆盖本地数据。
- 导出包结构：`{ app: 'whatelse', schemaVersion: 1, exportedAt, tasks, categories, settings }`
- 校验规则：空文本、非 JSON、JSON 数组、`app` 标识不符、版本号高于当前、缺 `tasks`/`categories` 数组——六种情况一律拒绝并给出中文原因。
- 需求编号：**F7.4**（见 3.9 节）。

**Q2：已完成任务的处理 —— 结论：永久保留，不做自动清理**

- 已完成任务**永久保留**，v1 不加「清空已完成」入口。
- `taskService.clearCompleted()` 函数已实现但暂不暴露给界面，留待 v1.1。
- 理由：数据量极小（1000 条任务约 250KB），自动清理的收益低于它对"翻旧账"的破坏。

**Q3：App 图标 —— 结论：由脚本生成，已落盘**

- **实物**：`static/logo.png`，192×192 RGBA，1746 字节。
- **规格**：圆角方形（半径 42px，约 22%），主色 `#3A7AFE` 铺底，中央白色对勾（折线 52,99 → 82,131 → 142,61，描边 19px，1.2px 抗锯齿），圆角外透明。
- **生成方式**：Python 标准库直接手写 PNG（zlib + struct，无第三方依赖）；生成脚本是一次性的，未留在仓库内。
- 云打包时在 `manifest.json` →「App图标配置」里选这张图，点「自动生成所有图标并替换」即可。

### 9.4 技术备忘（实现时的踩坑清单）

| 备忘 | 说明 |
| --- | --- |
| `appid` 不要手改 | `manifest.json` 里的 `appid` 由 DCloud 云打包时分配，手改会导致打包失败 |
| 标准基座可能不支持本地通知 | 真机调试 `createPushMessage` 时若无效，用「制作自定义调试基座」再试（7.9） |
| 通知渠道 `importance` 必须给 4 | 给低了通知只在通知栏静躺，不横幅、不响铃（7.7） |
| Android 权限必须精简 | 模板默认会塞进相机、通讯录、定位等无关权限，一律删掉（6.9） |
| 每次发版递增 `versionCode` | 否则覆盖安装会失败，只能先卸载（会丢数据） |
| 存储键名走 `keys.js` 常量 | 禁止在业务代码里手写字符串键名（6.10） |
| `delay` 单位是**秒** | 不是毫秒。计算方式 `Math.round((remindAt - Date.now()) / 1000)`（7.2） |
| 已完成的任务不再排提醒 | `scheduleTask` 中 `task.done` 直接 return（7.2） |
