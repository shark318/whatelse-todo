# 开源项目调研：为什么不直接拿现成的改

> 调研时间：2026-09 ｜ 调研平台：GitHub Search API
> 结论先说：**没有可以直接套用的项目**，从零写比"读懂一个陌生项目再改造"更快、更干净。

---

## 3. 逐个分析

### 3.1 `linzowo/uniapp-todolist` —— 最贴合，但用不了

| 项目 | 情况 |
| --- | --- |
| 描述 | 「采用 uniapp 框架开发的 microsoft 风格 todolist」 |
| Stars / Fork | 7 / 1 |
| 最后推送 | 2022-07-07（停更约 4 年） |
| License | **无** |
| 技术栈 | Vue 2、Vuex、`compilerVersion: 3` |

**实际看了它的文件结构**（通过 GitHub Contents API）：

```
App.vue              ← 37 KB！所有页面逻辑都塞在这一个文件里
main.js
manifest.json        ← 有完整的 app-plus 配置，说明支持 App 端
pages.json           ← 只有 945 字节，页面很少
components/
css/
pages/
static/
store/
uni.scss
unpackage/           ← 把构建产物也提交进仓库了
package-lock.json
```

**为什么不用**：

1. **没有 License** —— GitHub 上无 License 的仓库默认是「保留所有权利」，法律上不能拿来做二次开发分发。虽然自己改了自己用一般没人追究，但这属于明知故犯。
2. **停更 4 年** —— 基于 Vue 2（已停止维护）和旧版 uni-app 编译器，踩坑时搜不到任何社区支持。
3. **代码组织糟糕** —— `App.vue` 单文件 37 KB，说明没有做组件拆分；`unpackage/`（构建产物）也提交进了仓库。

**看它的 `manifest.json` 得到的唯一收获**：里面是一份典型的 HBuilderX 默认权限列表——包含了 `READ_CONTACTS`、`CALL_PHONE`、`READ_LOGS`、`CAMERA`、`ACCESS_FINE_LOCATION` 等一大堆与待办 App 毫无关系的敏感权限。**这正好印证了我们文档 6.9 节"必须手工精简 Android 权限"这条要求**：模板默认权限就是这么吓人。

### 3.2 `Memorydf/Smart-todo-app` —— 功能最全，但架构冲突

| 项目 | 情况 |
| --- | --- |
| 描述 | 基于 UniApp + Spring Boot + DeepSeek AI 构建的智能待办事项管理应用 |
| Stars | 2 |
| 最后推送 | 2026-05-11 |
| License | **MIT**（可自由使用） |
| 技术栈 | 前端 Vue 3 + Pinia；后端 Spring Boot 3 + MyBatis-Plus；AI 走 DeepSeek API 或本地 Ollama |

**它有什么**：完整的增删改查、分类管理、优先级设置、AI 自然语言生成待办、首页待办列表、AI 对话页、统计分析页、设置页。

**为什么不用**：

1. **强依赖后端** —— 需要一个 Spring Boot 服务常驻运行。而本项目的第一原则是"纯本地、不联网"。为了用它的代码，得先把整个后端拆掉，工作量比自己写更大。
2. **AI 功能对我们是负资产** —— 要联网调 DeepSeek API，涉及密钥管理、隐私与合规，全都在我们的"不做什么"清单里（开发文档 2.4 节）。
3. **它证明了需求方向是对的** —— 一个 2026 年的新项目仍然是"首页列表 + 分类 + 设置"这套结构，说明我们的页面设计方向没问题。**可以把它的页面清单当作设计交叉验证的参考。**

## 4. 唯一值得借鉴的：unibest

### 4.1 它是什么

| 项目 | 情况 |
| --- | --- |
| 仓库 | `feige996/unibest`（旧仓库 `codercup/unibest` 已停止维护） |
| Stars | 2266（旧仓库另有 2864） |
| 最后推送 | 2026-09-15（**非常活跃**） |
| License | MIT |
| 定位 | 「最好用的 uniapp 开发框架」——uni-app + Vue 3 + TS + Vite 5 + UnoCSS + WotUI 的**跨端快速启动模板** |
| 官网 | <https://unibest.tech> |

**它的 `package.json` 实际内容**（通过 GitHub Contents API 读取）：

- `engines`: `node >= 20`、`pnpm >= 9`
- 依赖：`@dcloudio/uni-app`、`vue ^3.4`、`pinia`、`pinia-plugin-persistedstate`、`vue-i18n`、`vue-router`、`z-paging`、`alova`、`dayjs`
- 开发依赖：`vite 5`、`unocss`、`typescript 5.8`、`eslint 9`、`vitest`、`sass`、以及 10 个 `@uni-helper/*` 构建插件
- 脚本：`dev:app`、`build:app`、`dev:mp-weixin` 等 40 多条，全部走 `uni` CLI

### 4.2 为什么不用它作为本项目的基座

| 原因 | 说明 |
| --- | --- |
| **它是脚手架，不是功能** | 它提供目录规范、请求封装、组件库、多端构建脚本，**一行待办功能都没有**。用了它，业务代码还是要从零写。 |
| **依赖太重** | 20+ 个运行时依赖 + 20 多个开发依赖。本项目只要 3 个页面，引入这套体系等于给一辆自行车装上飞机引擎。 |
| **路线冲突** | 它走的是 **CLI + pnpm + VS Code** 路线（`node >= 20`）。而本项目的既定路线是 **HBuilderX 可视化 + 云打包**。虽然 HBuilderX 也能打开 CLI 项目，但两者混用会引入额外的配置问题。 |
| **版本号带 alpha** | 它依赖的 `@dcloudio/uni-app` 版本号形如 `3.0.0-4070620250821001`，属于非稳定通道。个人工具项目不需要承受这种不确定性。 |
| **零依赖是我们的设计目标** | 开发文档 6.10 节写死了"第三方依赖保持 0 个"。这个决定直接换来的是：不会因为某个依赖升级而打包失败。 |

### 4.3 从它身上借鉴什么

| 借鉴点 | 如何体现在本项目 |
| --- | --- |
| 目录分层清晰 | 我们的 `pages/` + `components/` + `common/` 三层结构（开发文档 6.1）就是同一思路的极简版 |
| 组件命名规范 | `PascalCase.vue` 文件名（6.10） |
| 单一职责 | 页面只管渲染，逻辑下沉到 service（6.2） |
| 状态管理的取舍 | unibest 用 Pinia 做全局状态；我们只有 3 个页面、数据量极小，**改用 service + 页面局部状态**，省掉 Pinia 这一层 |

> 如果哪天这个 App 要变成"多人协作 + 多端上架"的正经产品，**再迁移到 unibest 也不迟**——那时候它的工程化能力才真正值钱。

## 5. 为什么最终决定自己写

| 判断维度 | 现成项目的实际情况 | 本项目的情况 |
| --- | --- | --- |
| **License** | 8 个候选里 **5 个无 License**（默认保留所有权利） | 自己写，无任何法律顾虑 |
| **可维护性** | 最好的那个（`linzowo`）停更 4 年、`App.vue` 单文件 37 KB | 自己的代码，结构和命名自己说了算 |
| **架构匹配** | 功能最全的（`Smart-todo-app`）要求后端常驻 | 纯本地、零后端、零依赖 |
| **技术栈匹配** | 多数是 Vue 2 或小程序优先 | Vue 3 + 仅 Android |
| **工作量对比** | 读懂一个陌生项目（且无文档）再改造 ≈ 1~2 天，且要不断和它的既有设计妥协 | 从零写 1500~2500 行、3 个页面，按第 8 章排期 1~2 天 |
| **可控性** | 出问题时要在别人的代码里找原因 | 每一行都是自己（或 AI 按本文档）写的 |

**一句话总结**：这个规模的项目，**"拿来改"的总成本高于"从零写"**，而且后者产出的代码结构与本文档完全一致，后续维护成本低得多。
